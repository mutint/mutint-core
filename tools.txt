# External (non-Python) tools this component needs, as conda package specs -- one per line,
# `#` comments ignored. The entry script collects these from every component the same way it
# collects requirements.txt, and installs them into env/tools with micromamba. Code finds
# them through mutint_common.tools.tool_path(), which falls back to PATH.
#
# Used by mutint_import/coverage.py to turn a bedGraph into the BigWig igv reads:
#     <weighted bedGraph> | sort | bedGraphToBigWig - sizes coverage.bw
#
# bedtools was here too, for `genomecov -ibam`, and is gone. Coverage now weights each
# alignment by 1/X1 -- breseq's redundancy tag -- and genomecov cannot express that: its
# -scale is one factor for the whole file, not per read. The counting moved into Python over
# pysam (see requirements.txt), which left bedtools with no caller in the suite, and a
# dependency every deployment installs and nothing uses is worse than one fewer.
#
# Not megadepth, which would have done the old job in one step: bioconda has no osx-arm64
# build of it, so an Apple Silicon machine would need an --platform osx-64 environment under
# Rosetta. This one builds natively everywhere.
ucsc-bedgraphtobigwig

# git, for `./mutint update` and the /update/ page: `mutint_common/update.py` asks the
# remote what is available with `git ls-remote` and moves this checkout onto it. It belongs
# here rather than in a prefix of its own -- unlike postgresql, which this file's header
# deliberately excludes -- because the test that file states is whether *application* code
# resolves the binary through `mutint_common.tools.tool_path()`, and this one does.
#
# Unpinned: any git can do what is asked of it here, and pinning would mean re-solving the
# tools every time conda-forge moves. Most machines already have one on PATH, which
# `tool_path()` falls back to; this is what makes an update work on a machine that does not.
# `install.sh` has its own bootstrap copy for the moment before this file can be read at all.
git
